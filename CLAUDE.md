# Working agreements

## Git workflow
- Commit directly to `main` and push to `main`. Do not create branches or pull requests unless asked.
- Group related changes into one commit per task. Every push to `main` triggers a Vercel production deploy, and the free plan limits deployments per day.
- Before pushing, run `npx tsc --noEmit` and `npx eslint` on the files you changed.
- Never force-push `main`.

## UI: mobile first
- The OKB Command Center is designed mobile first. For any UI work, build and check the phone layout (~390px wide) first, then add larger-screen layouts with `sm:`/`md:`/`lg:`/`xl:` or container queries (`@container`, `@xl:` …).
- Never let content get cut off or scroll sideways on a phone. Wide tables need a stacked card/row layout for narrow widths and show the table only where it fits (see `features/incident/components/incidents-view.tsx`).
- Every screen must stay usable with touch: tap targets at least ~40px, no hover-only actions.
- Check UI changes in a browser at 390px before pushing.

## Project notes
- Next.js app (App Router) deployed on Vercel; the Floodwatch data comes from `https://floodwatch-ten.vercel.app/` through `/api/floodwatch/*`.
- River basin study PDFs live in a Cloudflare R2 bucket (origin in `lib/config/study-storage.json`) and are served through the same-origin path `/studies/<id>.pdf` (rewrite in `next.config.ts`); until that is set, the viewer uses the Google Drive route. Pipeline scripts are in `scripts/river-basin-studies/` (`optimize_all.py`, then `upload-r2.mjs`). Each study is also split into ~3 MB standalone chunk PDFs (`split_pdfs.py` → `upload-r2-chunks.mjs`, manifest `lib/config/river-basin-chunks.json`); the viewer opens a study by loading its first chunk (one request) and prefetches the next, which avoids pdf.js's many serial range requests. Word documents are listed in `lib/config/river-basin-nonpdf.json` and shown with a Drive link.
- Waterway river tiles for the default view are pre-rendered into `public/waterway-tiles/v1/` (rebuild with `scripts/waterway-tiles/render.py`; filtered views and zoom 13+ use live tiles from `/api/waterways/tiles`).
- Vercel Blob (Hobby) is capped at 1 GB per store and is no longer used for the study PDFs.
- Maps (`features/map/`): the map is ready on `style.load`, not on `load` (which waits for every tile); add layers when `isStyleReady(map)` (`map.service.ts`), not `map.isStyleLoaded()`. On touch screens the canvas is capped at 2 device pixels, pinch only zooms, panels over a map lose their backdrop blur (`globals.css`) and marker animations pause while the map moves. Overlays over a map must only catch touches on their visible buttons (wrappers `pointer-events-none`), or pinches that start there fail.
- "Report a problem" (`features/feedback/`): a form (category, description, optional screenshot and contact) opened from the website footer and phone menu, the Command Center header (sm+) and phone navigation drawer, and the OKB Mobile help sheet. `POST /api/feedback` (multipart, rate-limited, honeypot) saves it in Supabase `okb_site_feedback` (SQL in `supabase/migrations/20261020000000_okb_site_feedback.sql`, also shown in Admin → Setup); screenshots go to the operations R2 bucket under `site-feedback/` and only signed-in admins can open them (`/api/admin/feedback/screenshot`). Admins work through them in Admin → Feedback (`features/admin/components/feedback-admin.tsx`): New → In progress → Fixed / Won't fix, with a private note.
- Road network data is bundled in `public/data/road-network/` (rebuild with `node scripts/build-road-network.mjs`); river basin outlines are in `public/data/river-basins/` (rebuild with `node scripts/build-river-basin-geo.mjs`).
- Program coverage names that the live accomplishment dashboard does not trace get their map location from `lib/config/coverage-geo.json` (OpenStreetMap; rebuild with `node scripts/build-coverage-geo.mjs`, add new names to its `SOURCES`).
- `/report-flood` is the mobile-only public flood report page (`features/flood-report/`): camera with GPS stamp + EXIF, up to 5 photos to the operations R2 bucket under `flood-reports/`, and optionally one video (Photo / Video switch; MediaRecorder, no sound, ~2.5 Mbit/s, stops at 50 MB or 5 min). Any browser works: when the browser does not let the page use the camera (Brave or Firefox blocking it, in-app browsers, no getUserMedia), the round button opens the phone's own camera app (`<input capture>`, photo or video); the picture comes back and gets the GPS stamp, and such a video has no GPS track (one pin). The page never asks for the camera by surprise or twice: when the browser would ask (`permissions.query` says prompt) it first shows "Turn on the camera" with a tip to make the browser remember Allow, and asks on that tap; a refusal is never retried, and a browser that already blocks the camera is not asked (browsers block a site's camera for days after a few closed or refused camera questions). A browser that never answers the camera request (UC Browser) gets the phone-camera screen after 8 s (`CAMERA_WAIT_MS`); a late answer still turns the camera on. Location is asked after the camera question is answered (or at once when location is already allowed, or while "Turn on the camera" is shown); `hooks/use-geolocation.ts` also takes a quick Wi-Fi / cell fix (±150 m or better) until the GPS answers, because Brave and Firefox do not use Google's location and their first GPS fix can take a minute or more. The video's first frame with the GPS stamp is saved as a JPEG poster (uploaded like a photo) and is the pin's picture when the report has no photo (▶ badge); the video goes straight to R2 with a signed link from `POST /api/flood-reports/videos` (needs the bucket CORS rule, set by `ensureDirectUploads`; under 4 MB it can go through the site) and is stored as `record.mobile.videos` (kept through edits, deleted with the report, streamed by `/api/flood-reports/media`). Then a form. The form asks for the DEO (optional: a Metro Manila list from `NCR_DEOS` in `lib/options.ts`, "Other…", or blank; the geocode route suggests the DEO of the nearest national road, `nearestDeo` in `features/incident/server/roads.ts`); it is saved as `extraction.administrative.districtEngineeringOffice`, so the bridge's PDF/text DEO column shows it instead of "OKB Mobile (public report)". Reports are written into `okb_bridge_reports` as platform `okb_mobile`, status `needs_review` (shown in Incoming Reports and on the flood maps; reviewed in Supabase directly, not through the bridge). `extractionMeta.extractedAt` stays null so the bridge's consolidated WhatsApp report skips unverified public reports. The site-wide `Permissions-Policy` allows `camera=(self)` (`next.config.ts`): it must be on every page, because opening the report page from a Command Center link keeps the policy of the page it came from. Photos taken far apart draw the flood as a stretch of road instead of one pin (`features/flood-report/server/stretch.ts`, standards in `lib/stretch.ts`, stored as `record.mobile.stretch` at submit/edit): the two farthest photos with GPS within ±50 m are the ends; under 50 m apart is one spot, over 2 km too far; photos more than 3 h or over 60 km/h apart are not trusted; both ends must be within 35 m of a road and connected by a route at most 1.6× the straight distance + 100 m: first the national roads in `roads.geojson`, else OpenStreetMap streets through the FOSSGIS OSRM walking service (`routing.openstreetmap.de`, only called for such reports); older reports are checked again on their next edit. A video is placed by the GPS track the camera records while filming (`record.mobile.videos[].track`, about one fix a second, fixes over ±30 m left out; its last frame is saved as `endPosterKey`): the start and end are the averages of its first and last 3 s; if the phone moved less than 10 m (or less than the GPS error) it was filmed steady and stays one pin, otherwise the same distance, speed and road checks draw the stretch from the start of the video to its end (used when the photos give no stretch, or there are fewer than 2 photos); the AI checks its first and last frames. Only then the photos go to Claude (`server/photo-check.ts`, needs `ANTHROPIC_API_KEY`; skipped when unset): photos without floodwater are dropped and the stretch is worked out again. Anything else stays one pin, with the reason in the details sheet and Admin → Reports; the stretch is drawn on the public map (pin halfway, a dot at each end) and on the Incidents map. On the Incidents flood map (`features/incident/server/flood-map.ts`) each mobile report stands on its own, as on the public map: its own GPS spot (location key `mobile:<report id>:<index>`), shown until it receded or its time is up, never hiding or hidden by other reports of the same road (WhatsApp / Viber reports are grouped by road, the newest deciding). Without a receded time a mobile report leaves the public map and the Incidents flood map by the sender's weather: 2 h clear, 3 h cloudy, 4–6 h rain, at least 4 h while PAGASA reports rain (`features/flood-report/lib/expiry.ts`); its photos show in the Incidents flood alert panel and location cards. Senders can mark their report receded, edit it, delete/add photos or delete it: submit returns a secret edit key kept in the phone's browser (`lib/my-reports.ts`), only its SHA-256 is stored (`record.mobile.ownerTokenHash`); `/api/flood-reports/[id]` (PATCH/DELETE) and `/api/flood-reports/mine` check it. An approved report edited (other than its receded time) goes back to needs review; a report linked to an incident cannot be deleted. The bridge's automated WhatsApp report (text + PDF with photos) includes a mobile report only when `record.mobile.inConsolidated` is set at submit: the sender's IP is in `OKB_MOBILE_REPORT_TEST_IPS` (comma list, or `all`); `/api/flood-reports/whoami` shows a phone's IP. The bridge reads these reports from Supabase when it makes a report. Operators manage reports in Admin → Reports (`features/admin/components/mobile-reports.tsx`, `/api/admin/mobile-reports`, admin sign-in): mobile reports (edit details, delete/add photos, add videos, delete; an operator edit keeps the review status) and WhatsApp / Viber reports (add/delete photos and videos, delete). WhatsApp / Viber flood reports also show on the public map (`server/bridge-reports.ts`): one pin per flooded location, placed by its coordinates or on the road network on the server (`features/incident/server/roads.ts`; `roads.geojson` is bundled via `outputFileTracingIncludes`), flooded exactly while the Incidents map shows it; the public text has phone numbers and e-mail addresses removed. Photos and videos operators add to any report live in R2 under `report-media/<report id>/` (`server/media.ts`, served with Range by `/api/flood-reports/media`, uploaded straight to R2 from Admin → Reports), never in the report record, so the bridge cannot overwrite them; they show on the public map and in the Incidents panels. WhatsApp / Viber reports are deleted through the bridge (`DELETE /api/v1/reports/:id`, so they leave its memory and automated reports); any delete first removes the report's `okb_bridge_consolidated_report_items` rows (foreign key, restrict). On opening, a speech bubble over the Help button gives the three steps to send a report (`components/help-tip.tsx`; every visit until closed, remembered in localStorage `okb-report-help-tip-done`). Visitors react to and comment on each photo and video on the map (shown under each photo as soon as the viewer opens, "Hide" folds it away; counts on the details photos): the Gallery's reactions and anonymous comments (`features/gallery/server/engagement.ts`, tables `okb_gallery_reactions` / `okb_gallery_comments`, item key `flood:<storage key>`, accepted only for media of an existing report; removed when the report is deleted; hide a comment with `hidden = true` in Supabase). The photo viewer renders in a portal on `document.body` (the details sheet is moved with a transform). The map legend opens a sheet explaining each color (`components/map-legend.tsx`); receded is violet so it stands apart from the green "Low". On phones every Command Center page shows a floating "Report a flood" button (`features/flood-report/components/report-flood-fab.tsx`, mounted in `command-shell.tsx`; round on full-screen map pages, can be tucked into an edge tab).
